## Local tier architecture

The local tier is complete on its own; the cloud adds only remote reach, alerts, history and multi-site.

- **`local` topology field** — per-controller options (`buttons`, `ui`, `rtc`) on `Controller.local`, schema 19, `src/lib/topology.types.ts`.
- **Panel buttons** — `src/lib/codegen/generators/local-inputs.ts` maps board digital inputs (KC868-A16 IN1–IN16) to actions: IN1 is always Stop All, each later input toggles one route. Auto-assigned by default; an explicit `local.buttons` overrides.
- **Automation persistence** — `firmware/components/maji_automations` saves the last-good set to NVS on every apply and restores it at boot through the same validation path; schedules survive reboots and power cuts with no server.
- **On-device dashboard** (`local.ui`) — the `maji_local_ui` component replaces the stock ESPHome web_server page and serves the operator dashboard from flash: `GET /`, `GET /local/state` (SSE), `GET /local/automations` (wire blob), `POST /local/command`, `POST /local/automations`. The device-mode app is built ONCE with `npm run build:device` (no site-config argument — nothing is baked per site): `dist/device/browser` holds every asset pre-gzipped (`<name>.gz`) plus `device-ui-manifest.json` (`{ version: 1, assets: [{ path, file, contentType, immutable }] }`). The server hosts that directory raw at `/device-ui/` (`MAJI_DEVICE_UI_DIR`, baked to `/app/device-ui` in the image — no `Content-Encoding`, the browser gunzips); the codegen fetches the manifest + assets from there at bundle-generation time and embeds them into `local-ui-assets.h`. The site topology rides the firmware the same way: the device serves `/topology.json`, which the app fetches at runtime (`src/app/device/device-topology.ts`) — so one build serves every site. App bundle uses hash-location + index fallback for SPA routes. SSE slots are released only via the httpd `free_ctx` destroy callback — never recycle a slot from the stall path. Automations edit on-device works end-to-end: `DeviceAutomationsService` (swap in `device.providers.ts`) list/mutate via `GET`/`POST /local/automations` (decoder in `src/lib/automation-wire.ts`); names live in localStorage. Setup (safety timings, route defaults, calibration) also edits on-device: `DeviceBackendService.writeControllerConfig` sends one `config_set` command per key over `/local/command`, the device persists each via `restore_value`, and the applied values ride the snapshot `readings` back into the same fields. The Activity feed renders on-device too: the snapshot carries an `events[]` ring (newest-first, max 10 — `SnapshotEvent` in `src/lib/codegen-ids.ts`), surfaced by `DeviceRealtimeService.recentDeviceEvents`/`subscribeDeviceEvents` and mapped to the shared activity rows in `src/app/device/device-activity.ts`. Commands from this app tag `actor: 'local-ui'` in the envelope; panel buttons tag `panel`. Both are reserved actor ids (`RESERVED_ACTOR_LABELS`) — the server labels them at ingest ("Panel button" / "On-device dashboard"), the on-device feed from the same map. One shell serves both builds: `src/app/pages/dashboard/dashboard.component.ts` is the widget-grid dashboard on cloud and device — the device build swaps Realtime/Backend/Automations/Layout via `device.providers.ts` (layouts persist to PocketBase on cloud, localStorage on-device via `DeviceLayoutService`) and drops cloud-only widgets (history charts, usage totals, health history) through the registry's `cloudOnly` flag (`filterForBuild`, `src/app/widgets/registry.ts`).
- **RTC** (`local.rtc`) — optional DS3231 on the board I2C bus (0x68) so time-based schedules run fully offline. Default is SNTP-only; time is trusted after a valid RTC boot read or a real SNTP sync (`src/lib/codegen/generators/time-sync.ts`).

## Dashboard (one shell, two builds)

`src/app/pages/dashboard/dashboard.component.ts` is THE site dashboard in both the cloud and on-device builds (the old component and the `new_dashboard` flag machinery are gone; spec `docs/dashboard-rework-spec.md`).

- **Registry** — `src/app/widgets/registry.ts` (pure TS `WidgetDef` + `filterByEntitlement`/`filterForBuild`); def table `pages/dashboard/widget-defs.ts`; instance→component union `pages/dashboard/widgets.ts`. `cloudOnly` defs (charts, usage, health, billing widgets) drop out of the device build at one filter point.
- **Layout** — `dashboard_layouts` collection (migration 61: `key`, `site`, `user` empty = site default, unique on the triple); resolution user → site default → auto-derived (`src/app/widgets/layout.ts`). On-device, `DeviceLayoutService` (provider swap) persists to localStorage. `LayoutItem.section` zone labels are curated-default-only — storage strips them.
- **Default zones** — Routes → Map (desktop-only) → Status & controls (tanks/valves/pumps; hidden on desktop where the map absorbs them, the phone's map substitute) → Usage → System → Trends (`default-layout.ts`). Attention banner above the grid: faults, offline controllers, safety override.
- **Capabilities** — `GET /api/farmon/sites/{id}/capabilities` → `{ capabilities, widget_ids }`, resolved by `internal/entitlements.Set` (the single evaluator; `billing.HasCapability` wraps it). Frontend: `CapabilitiesService` (skips on-device).
- **Grid** — `src/app/widgets/widget-grid.component.ts`: hand-rolled CSS grid (12/4/1 col), edit mode ≥640px (drag-reorder, width cycle, hide + picker); phone is read-only layout.

## Tenant billing + Shengda meters

Cloud-only module (migrations 57–59; spec `docs/billing-shengda-implementation-spec.md`, domain model `docs/billing-module-architecture.md`). Battery-powered Shengda ultrasonic meters (NB-IoT/Cat.1, built-in valve) report cumulative readings over raw UDP — no field controller, no MQTT, no auth at the wire layer (accepted risk; mitigation: only claimed meters feed billing, valve commands echo the device-reported IMEI, new-source-IP events).

- **Codec** — `maji-server/internal/metering` (frame parse/build, CBOR objects). CRC16 is AUG-CCITT (SPI-FUJITSU), big-endian, full frame minus CRC — locked by fixture tests; the vendor PDF's time-calib hex has a one-byte typo (extra `62`), corrected in the spec. Reading dedupe key is `(meter, message_id, device_ts)` — the wire's message ID is a random 16-bit value and collides on its own. Readings store integer **millilitres** (wire reports litres; convert at ingest).
- **Sessions** — meters sleep; downlink is possible only in the ~20s window after an uplink: reply time-calib immediately (SN must echo), flush ONE queued command, match its ack (FuncCmdResult) by IMEI. `meter_commands` is the persistent queue: queued → sent → acked | expired (48h TTL sweeper).
- **Billing spine** — `maji-server/internal/billing`: scheduler (create_cycle → prepare_invoices from boundary readings × tariff → daily mark_overdue), manual payments allocated oldest-debt-first, arrears automation (overdue > grace_days → warn → > warn_days → `valve_close`; settled → `valve_open`; `rule:arrears` actor id; never closes unwarned; idempotent via `warned_at`/`closed_at` + pending-valve guard). Money is integer minor units everywhere.
- **Gating, two layers** — global `billing_module` feature flag (UI routes) + per-site `tenant_billing` capability (`sites.addons` ∪ `packs.capabilities`, `billing.HasCapability` on every route/job). Entitlement fields are admin-only writes (`guardEntitlement*` in `sites_hooks.go`).
- **Listener** — starts only on the cloud binary when `MAJI_METER_UDP_ADDR` is set. Dashboard: `site/:name/billing/*` (Angular), valve actions need typed confirmation; queued commands always show "pending — applies at next meter contact (up to 24h)".

## Partner portal

Cloud-only (spec `docs/partner-portal-spec.md`), flag `partner_portal` + `roleGuard` partner-only on `/partner`, `/partner/org`, `/partner/customers/new` (`src/app/pages/partner/`); the nav entry lives in the shared `#navLinks` template and `home` routes partners to `/partner` when the flag is on. The partners collection stays admin-only: self-serve org profile goes through `/api/farmon/partner/org` GET/PATCH + logo POST (`internal/api/partner_routes.go`, org resolved from `e.Auth.partner`, never the body); `/api/farmon/branding` serves the same record to any org member (BrandingService reapplies on `refresh()`). Partners READ `notification_incidents` for their org's sites via the 49/55 rule chain (migration 62 is only a checkpoint — its up is a byte-identical no-op, kept for numbering); migration 63 restricts the org-scoping partner clause (55/61/62) to `role = "partner"` — customers carry `users.partner` too, so the unguarded clause leaked the whole org's sites to any customer. Multi-request HTTP e2es (wizard, branding propagation) build ONE mux and fire sequential requests — a second `apis.NewRouter` on a shared TestApp double-binds OnServe hooks and panics.
