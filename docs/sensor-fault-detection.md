# Sensor Fault Detection

## Overview

MajiFlow generates ESPHome firmware with built-in sensor fault detection for inline flow sensors. This document describes the detection algorithm, thresholds, and integration with Home Assistant.

## Detection Algorithm

When the pump is in the RUNNING state and valves are open on the active route, each flow sensor on that route should report non-zero readings. A zero reading in this state indicates one of two conditions:

1. **No flow** (pipe blockage, dry source, pump failure) — handled by the existing `no_flow` fault code
2. **Sensor fault** (broken sensor, wiring issue, debris on impeller) — handled by sensor fault detection

### Distinguishing no_flow from sensor_fault

The key distinction is **timing**:

- **no_flow**: Flow was never established after `flow_confirm_seconds`. This triggers a system FAULT and kills the pump.
- **sensor_fault**: Flow was confirmed (readings > 0.5 L/min), then dropped to zero while the pump is still running. This suggests the sensor stopped reporting, not that flow actually stopped.

### Counter Logic

For each flow sensor, a counter `{sensor_id}_fault_count` tracks consecutive zero readings:

1. When pump is RUNNING and the sensor is on the active route:
   - If reading > 0.5 L/min → reset counter to 0 (healthy)
   - If reading ≈ 0 and flow was previously confirmed → increment counter
2. When counter reaches **3** consecutive zero readings → `sensor_fault` binary_sensor becomes `true`
3. Counter resets to 0 when:
   - A non-zero reading is received
   - Pump returns to IDLE state

### Why 3 consecutive readings?

A single zero reading can occur due to:
- Momentary air pocket in the line
- Sensor read timing (pulse counter window alignment)
- Electrical noise

Three consecutive readings at the default 5-second update interval means 15 seconds of sustained zero flow — long enough to rule out transients.

## Generated ESPHome Components

For each flow sensor, MajiFlow generates:

### Global variable
```yaml
globals:
  - id: flow1_fault_count
    type: int
    initial_value: '0'
```

### Binary sensor (exposed to HA)
```yaml
binary_sensor:
  - platform: template
    id: flow1_sensor_fault
    name: "Flow 1 Sensor Fault"
    icon: "mdi:alert-decagram"
    device_class: problem
    entity_category: diagnostic
    lambda: return id(flow1_fault_count) >= 3;
```

### Updated on_value lambda
The flow sensor's `on_value` lambda includes fault counter logic alongside the existing flow confirmation and watchdog integration.

## Home Assistant Integration

### Suggested Automation: Alert on Sensor Fault

```yaml
automation:
  - alias: "Alert: Flow Sensor Fault"
    trigger:
      - platform: state
        entity_id:
          - binary_sensor.pump_ctrl_flow1_sensor_fault
          - binary_sensor.pump_ctrl_flow2_sensor_fault
        to: "on"
    action:
      - service: notify.mobile_app
        data:
          title: "Sensor Fault Detected"
          message: "{{ trigger.to_state.name }} — check wiring and sensor."
          data:
            tag: "sensor-fault"
            importance: high
```

### Monitoring Repeated Faults

If `sensor_fault` triggers repeatedly (e.g., >3 times in 24 hours), the sensor should be considered unreliable. A suggested HA automation:

```yaml
automation:
  - alias: "Flag: Unreliable Sensor"
    trigger:
      - platform: state
        entity_id: binary_sensor.pump_ctrl_flow1_sensor_fault
        to: "on"
    condition:
      - condition: template
        value_template: >
          {{ states.counter.flow1_fault_daily.state | int(0) >= 3 }}
    action:
      - service: persistent_notification.create
        data:
          title: "Unreliable Sensor"
          message: "Flow sensor 1 has faulted 3+ times today. Inspect or replace."
```

This requires a HA `counter` helper that resets daily — not generated by MajiFlow, as it's a HA-side concern.

## Limitations

- Sensor fault detection only operates during pump RUNNING state
- Cannot detect a sensor that reads artificially high (stuck value) — only detects zero readings
- The 3-reading threshold is hardcoded in firmware; changing it requires regeneration
- Fault counter resets on pump stop, so intermittent faults across separate pump cycles require HA-side tracking
