# Transport Driver Framework

Baseline framework for defining I/O provider drivers. Every driver must address
the safety requirements in this document before shipping.

## Driver Contract

Every transport driver is a **factory** that binds its config and returns an `IoProviderDriver`:

```typescript
function createXxxDriver(config: XxxConfig): IoProviderDriver
```

The factory is type-safe. The returned driver is context-free — composable, storable, no generics.

### Required Methods

| Method | Purpose |
|--------|---------|
| `enumerate()` | List available channels with capabilities (`IoChannel[]`) |
| `resolve(channelId, usage)` | Return ESPHome platform + config for a channel (`ResolvedChannel`) |

### Optional Methods

| Method | Purpose |
|--------|---------|
| `consumedPins()` | Board pins consumed by the provider's infrastructure (auto-reserved) |

### Future Methods (added when first non-board driver ships)

| Method | Purpose |
|--------|---------|
| `prerequisites()` | Generate ESPHome YAML blocks needed before entity codegen (modbus_controller, cd74hc4067 component, etc.) |

## Safety-Critical Platform Compatibility

Entity codegen emits safety attributes AFTER the transport header. Not all
ESPHome platforms support all attributes. This matrix defines what works
where and what must be replaced with software equivalents.

### Actuator Attributes (hardware.yaml — switch: section)

| Attribute | Purpose | `gpio` | `gpio` + PCF8574 | `modbus_controller` switch |
|-----------|---------|--------|-------------------|---------------------------|
| `interlock: [a, b]` | Mutual exclusion for valve open/close pairs | Yes | Yes | **NO** |
| `interlock_wait_time` | Delay between interlock transitions | Yes | Yes | **NO** |
| `restore_mode: ALWAYS_OFF` | Safe power-on state (relays de-energized) | Yes | Yes | **NO** |
| `internal: true` | Hide from the published entity set | Yes | Yes | Yes |
| `on_turn_on` / `on_turn_off` | Automation triggers (pump refcount guard) | Yes | Yes | Yes |

### Sensor Attributes (sensors.yaml — sensor: section)

All ESPHome sensor platforms inherit from the base Sensor component.
These attributes work on **all** platforms:

| Attribute | Purpose | `adc` | `pulse_counter` | `modbus_controller` | `cd74hc4067` | `ads1115` |
|-----------|---------|-------|-----------------|---------------------|-------------|-----------|
| `filters:` | Median, calibration, lambda | Yes | Yes | Yes | Yes | Yes |
| `on_value:` | Fault detection, flow confirm | Yes | Yes | Yes | Yes | Yes |
| `unit_of_measurement` | Dashboard display | Yes | Yes | Yes | Yes | Yes |
| `update_interval` | Polling rate | Yes | Yes | Yes* | Yes | Yes |

*`modbus_controller` sensors default to the controller's global interval but can override per-sensor.

## Missing Safety Features — Required Software Equivalents

When a platform does NOT support a safety-critical attribute, the driver
or entity codegen MUST provide a software equivalent.

### `interlock` (Valve open/close mutual exclusion)

**Affects**: `modbus_controller` switches (Modbus DIO driver)

**Software equivalent**: Add `on_turn_on` lambda to each switch that turns off the sibling:

```yaml
- platform: modbus_controller
  id: valve1_open_pin
  on_turn_on:
    - switch.turn_off: valve1_close_pin
    - delay: 100ms
```

This must be generated by the valve entity codegen when it detects the transport
is not `gpio`. The entity can check `ResolvedChannel.platform` to determine this.

### `restore_mode: ALWAYS_OFF` (Safe power-on default)

**Affects**: `modbus_controller` switches

**Required**: Verify that the physical Modbus relay module defaults to all
relays OFF on power-up. Most industrial relay modules (Waveshare, Kincony)
do this by default. Document the requirement in the driver's README.

If the module does NOT default to OFF, the driver's `prerequisites()` must
generate an `on_boot` action that explicitly turns off all relay coils.

## Transport Limitations

| Transport | Max update rate | Suitable for | NOT suitable for |
|-----------|-----------------|-------------|------------------|
| Native GPIO | Microseconds | Everything | — |
| PCF8574 (I2C expander) | ~1ms per read | Digital I/O, relays | Pulse counting, ADC |
| Modbus RTU @ 9600 baud | ~20ms round trip | Low-freq digital, analog | Pulse counting >25 Hz |
| Modbus RTU @ 115200 baud | ~2ms round trip | Digital, analog, low-freq pulse | Pulse counting >250 Hz |
| CD74HC4067 (analog MUX) | ~2ms per channel switch | Multiplexed ADC | Digital output, pulse counting |
| ADS1115 (I2C ADC) | ~7ms per conversion | High-precision ADC (16-bit) | Digital I/O, pulse counting |

### Capability Matrix

| Transport | `digital_out` | `digital_in` | `adc` | `pulse_counter` |
|-----------|:---:|:---:|:---:|:---:|
| Native GPIO | Yes | Yes | Yes | Yes |
| PCF8574 | Yes | Yes | No | No |
| Modbus DIO | Yes | Yes | No | Low-freq only* |
| Modbus ADC | No | No | Yes | No |
| CD74HC4067 MUX | No | No | Yes | No |
| ADS1115 | No | No | Yes | No |

*Low-frequency pulse counting via software edge detection on polled Modbus discrete inputs. Only suitable for large-pipe flow meters outputting <25 Hz.

## Safety Checklist for New Drivers

Before shipping a driver PR, verify:

- [ ] All relay/valve outputs default to OFF on power-up (hardware or software)
- [ ] Mutual exclusion enforced for valve open/close pairs
      - GPIO/PCF8574: `interlock` attribute (hardware)
      - Other: `on_turn_on` / `on_turn_off` software interlock (documented above)
- [ ] Pump refcount guard works (`on_turn_on` lambda supported by platform)
- [ ] Flow sensor fault detection works (`on_value` lambda supported by platform)
- [ ] Tank level suppression during route operation works (lambda filter supported)
- [ ] Board pins consumed by provider infrastructure are auto-reserved via `consumedPins()`
- [ ] Channel capabilities are accurate — no false `pulse_counter` on I2C-polled inputs
- [ ] Update rate is documented — don't assign high-frequency sensors to slow transports
- [ ] ESPHome compilation tested with generated YAML for at least one board (Heltec V3 or KC868-A16)
- [ ] All existing tests pass (`npm test`, topology, selftest, limits)

## Implementing a New Driver

### 1. Create the driver file

```
src/lib/io-providers/{transport}-driver.ts
```

Export a factory function:

```typescript
export function createXxxDriver(config: XxxConfig): IoProviderDriver {
  return {
    enumerate() { /* return IoChannel[] */ },
    resolve(channelId, usage) { /* return ResolvedChannel */ },
    consumedPins() { /* return string[] of board pins used by infrastructure */ },
  };
}
```

### 2. Register in the driver registry

When the second driver ships, introduce `src/lib/io-providers/registry.ts`
with a `Map<string, (config) => IoProviderDriver>`. Until then, the board driver
is the only driver and needs no registry.

### 3. Add topology schema support

Add `io_providers` to `DeviceSchema` in `schemas.ts` and `device` type in
`topology.types.ts`. Each provider entry has `{ id, type, config }`.

### 4. Update `buildResolveChannel()`

Extend to accept `io_providers[]`, create driver instances, route `provider:CHANNEL`
IDs to the right driver.

### 5. Add prerequisite emission

Extend `device-yaml.ts` to call `driver.prerequisites()` and emit the YAML
before entity codegen.

### 6. Verify against safety checklist

Complete every item in the checklist above. Document any gaps in the PR description.
